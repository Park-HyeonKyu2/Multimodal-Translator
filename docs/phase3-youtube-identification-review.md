# Phase 3-4 검토: YouTube 영상·브라우저 탭 식별

작성일: 2026-10-26 · 성격: **검토 문서** (코드 변경 없음) · 대상: 로드맵 Phase 3 "YouTube 영상 ID 식별 확장 기능 검토"

## 1. 결론 요약

- 지금(3-1~3-3)은 브라우저를 `app:chrome.exe`처럼 **프로그램 하나 = 콘텐츠 하나**로 본다. 창 제목과 주소는 읽지도 저장하지도 않는다 (사용자 결정, 2026-10-26).
- 영상·탭 단위 식별이 **정말 필요한지는 아직 모른다.** 박스 위치는 영상이 바뀌어도 거의 같고, 필요한 것은 Phase 4의 문맥 기억을 어떤 단위로 나눌지다. 이 판단에는 Phase 4의 실험 근거가 필요하다.
- 후보 다섯 가지를 비교한 결과, **지금 구현을 시작하지 않는 것을 권고**한다. 필요해지면 다음 순서로 시도한다.
  1. **Windows 미디어 세션(SMTC)**: 설치 없이 영상 제목·채널을 알 수 있다. 이 PC에서 가능함을 확인했다 (§4.2). 새 의존성이 필요하다.
  2. **브라우저 확장 + 네이티브 메시징**: 영상 ID까지 정확히 알 수 있지만 설치·배포·권한 부담이 크다. 1번으로 부족할 때만 시도한다.
- 거부하는 방식: 원격 디버깅 포트, 화면 OCR로 제목 읽기, 로컬 HTTP 서버 방식 (이유는 §4).
- **어떤 방식이든 YouTube API를 호출하지 않는다.** API를 쓰면 약관 의무(데이터 30일 보관 제한, 개인정보 처리방침 등)가 붙는데, 영상 ID나 제목은 사용자 PC에서 로컬로 읽을 수 있어 API가 필요 없다.

## 2. 먼저 정해야 할 것: 무엇을 나누려는가

"콘텐츠"에는 목적이 다른 두 단위가 섞여 있다.

| 용도 | 알맞은 단위 | 이유 |
| --- | --- | --- |
| 바운딩 박스 설정 저장 (3-3) | 프로그램 또는 사이트 | 자막 위치는 같은 플레이어 안에서 영상마다 거의 같다. 영상별로 나누면 영상마다 박스를 다시 만들어야 한다 |
| 문맥 기억 (Phase 4) | 영상·시리즈·채널 (가설) | 등장인물 이름, 용어, 말투는 같은 시리즈에서 이어진다. 프로그램 단위로는 서로 다른 채널의 기억이 섞인다 |

따라서 **박스용 ID와 기억용 ID를 같은 값으로 묶을 필요가 없다.** 박스는 지금 구조(프로그램 단위)를 유지하고, 기억용 키만 나중에 더 세밀하게 만드는 편이 안전하다. 기억 단위가 영상인지 채널인지는 가설이며, 실험으로 정해야 한다 (§7).

## 4. 후보별 상세

확인 수준을 구분해 적는다: **[실측]** 이 PC에서 직접 확인 · **[자료]** 공식 문서로 확인 · **[미확인]** 확인하지 못함.

### 4.1 A. 창 제목

- 브라우저 창 제목은 `<페이지 제목> - <브라우저 이름>` 형태다. **[실측]** 이 PC의 Chrome 창 제목은 마지막 ` - ` 뒤가 `Chrome`이었다 (제목 내용은 읽지 않고 접미사만 확인).
- 영상 ID가 없다. 같은 영상도 알림 개수 같은 접두사가 붙거나 재생 목록에 따라 제목이 바뀔 수 있다. **[미확인]** 변동 정도는 측정하지 않았다.
- 제목에는 사용자가 보는 모든 페이지의 내용이 들어 있어, 우리가 정한 "창 제목을 읽지 않는다" 원칙과 충돌한다.

### 4.2 B. Windows 미디어 세션 (SMTC)

- `GlobalSystemMediaTransportControlsSessionManager`는 시스템의 재생 세션 정보를 제공한다. **[자료]** Windows 10 1809(10.0.17763) 이상, 패키지 앱은 `globalMediaControl` 기능이 필요하다 ([Microsoft Learn](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessionmanager)).
- **[실측]** 이 PC(Windows 11, Chrome에서 재생 중)에서 PowerShell 5.1로 조회하니 세션 1개가 잡혔고 앱 ID는 `Chrome`, 제목·아티스트 값이 있었으며 상태는 재생 중이었다. 값의 내용은 출력하지 않고 존재 여부만 확인했다. 패키지되지 않은 데스크톱 프로그램에서 조회되므로 Python 앱도 가능할 것으로 보나, **[미확인]** Python 바인딩으로는 시험하지 않았다.
- 한계:
  - 영상 ID가 없다. 제목과 채널(아티스트)만 알 수 있다. 그래도 문맥 기억 키로는 채널 단위가 오히려 알맞을 수 있다 (§2).
  - 재생 중이거나 직전까지 재생된 미디어만 잡힌다. 일시정지가 오래되면 세션이 사라지는지는 **[미확인]**이다.
  - **세션이 현재 보고 있는 탭과 같다는 보장이 없다.** 다른 탭에서 영상이 재생 중인 채 사용자가 다른 탭을 보면 잘못 식별한다. 활성 창이 브라우저인지(3-1 결과)와 세션의 앱이 같은 브라우저인지를 함께 확인해도, 탭 단위 오판은 남는다. 미디어를 재생하지 않는 페이지(문서, 이미지 영상)는 식별되지 않는다.
  - Chrome 외 브라우저(Edge, Firefox)의 동작은 **[미확인]**이다.
  - YouTube인지 다른 사이트인지는 세션만으로 알 수 없다 (제목·채널만 있다).
- 의존성: Python에서 부르려면 WinRT 바인딩 패키지(예: `winrt-Windows.Media.Control` 계열)가 필요하다. 프로젝트 규칙(새 의존성은 분명한 이유가 있을 때만)에 따라 **도입 전에 사용자 승인이 필요하다.** 호환 버전과 라이선스는 **[미확인]**이다. PowerShell을 호출하는 방법은 매번 프로세스를 띄워 느리므로 쓰지 않는다.
- 개인정보: 미디어 제목은 시청 기록 성격이다. 저장한다면 로컬에만 두고, 저장 값은 해시(식별만 필요한 경우)나 채널명으로 줄인다.

### 4.3 C. UI Automation으로 주소창 읽기

- 주소창의 접근성 이름("Address and search bar" 등)으로 요소를 찾아 값을 읽는 방법이 자동화 커뮤니티에서 쓰인다. **[자료: 비공식]** 표시 언어에 따라 이름이 달라 번역이 필요하다는 보고가 있다. 공식 문서는 찾지 못했다.
- 브라우저 화면 구조 변경에 취약하고, 읽는 순간 모든 탭의 주소에 접근할 수 있는 코드가 생긴다. 안정성과 개인정보 면에서 D보다 불리하다. **[미확인]** 이 PC에서는 시험하지 않았다.

### 4.4 D. 브라우저 확장 + 네이티브 메시징

구성: 확장이 활성 탭 정보를 네이티브 호스트(우리 앱이 띄우는 프로세스 또는 별도 실행 파일)로 보낸다.

- **[자료]** 호스트 매니페스트는 JSON이고 `allowed_origins`에 허용할 확장 ID를 **구체적으로** 적어야 한다 (와일드카드 불가). Windows에서는 `HKCU\Software\Google\Chrome\NativeMessagingHosts\<호스트 이름>` 레지스트리 키에 매니페스트 경로를 등록한다. `runtime.connectNative`는 포트가 열려 있는 동안 호스트 프로세스 하나를 유지하고 `sendNativeMessage`는 메시지마다 새로 띄운다 ([Chrome 문서](https://developer.chrome.com/docs/apps/nativeMessaging/)).
- 장점: 영상 ID(URL의 `v=` 값)를 정확히 얻고, 탭 전환과 페이지 이동을 이벤트로 받는다. 권한을 YouTube 주소로 제한하면 다른 사이트의 탭 정보는 보지 못한다.
- 부담:
  - 사용자가 확장을 설치하고 호스트를 등록해야 한다. 배포 방법(스토어 심사 또는 개발자 모드)은 **[미확인]**이다.
  - 브라우저마다 매니페스트 형식과 레지스트리 경로가 다르다 (Chrome, Edge, Firefox 각각).
  - 확장 서비스 워커의 수명 관리 같은 구현 세부는 **[미확인]**이다.
  - 우리 앱 밖에 코드가 하나 더 생겨 보안 검토 대상이 늘어난다.

### 4.5 E. 원격 디버깅 포트 — 거부

- **[자료]** Chrome 136부터 기본 프로필에서는 `--remote-debugging-port`를 무시한다. 쿠키 탈취 공격을 막기 위한 조치다 ([Chrome 블로그](https://developer.chrome.com/blog/remote-debugging-port)).
- 사용자의 평소 브라우저를 특수 옵션으로 다시 실행하게 만들어야 하고, 열린 포트는 모든 탭의 내용에 접근을 열어 준다. 보안 면에서 받아들일 수 없다.

### 4.6 F. 확장 + 로컬 HTTP 서버 — 비추천

- 설치는 D보다 쉬워 보이지만, 로컬 포트에 접속할 수 있는 다른 프로그램이나 웹페이지가 가짜 정보를 보내거나 정보를 읽을 수 있다. 인증 토큰과 허용 출처 검사를 직접 구현해야 하고, 그 비용이 네이티브 메시징을 쓰는 것보다 크다.

### 4.7 G. 화면 OCR로 제목 읽기 — 거부

- 이미 OCR이 있지만 "원본 화면 기본 미보관" 원칙과 맞지 않고, 제목 위치·글꼴이 사이트마다 달라 불안정하다. 얻는 정보도 A와 같다.

## 5. 약관·라이선스·개인정보

법률 자문이 아니라 공개 문서 기준의 정리다. 상용 배포 전에 최신 약관을 다시 확인한다.

- **YouTube 이용약관**: 로봇·스크래퍼 같은 **자동화된 수단으로 서비스에 접근하는 것**을 제한한다 (예외: 검색 엔진, 사전 서면 승인) ([약관](https://www.youtube.com/t/terms)). 이 검토의 방식들은 모두 **사용자 PC의 브라우저 정보를 로컬에서 읽는 것**이고 YouTube 서버에 접근하지 않는다. 다만 이 해석이 약관의 의도에 맞는지는 확정할 수 없다. 영상 제목이나 채널 정보를 얻으려고 YouTube 페이지를 우리 쪽에서 내려받는 기능은 만들지 않는다.
- **YouTube API 서비스 개발자 정책**: API로 얻은 데이터는 보관 기한(대부분 30일) 등 의무가 붙고, API 데이터를 API 외 기술로 얻는 것과 스크래핑을 금지한다 ([정책 III.E, III.I](https://developers.google.com/youtube/terms/developer-policies)). **API를 쓰지 않으면 이 의무가 적용되지 않는다.** 그래서 이 설계는 API 호출을 하지 않는다.
- **DRM·OTT**: 04 문서대로 DRM 우회는 지원하지 않는다. 유료 OTT 영상은 보호된 화면이 캡처에서 비어 보일 수 있다고 알려져 있으나 **[미확인]**이다. 이 문서 범위 밖이며 Phase 6 점검에서 따로 확인한다.
- **저장 원칙** (04 문서 + 3-1 결정): 영상 식별 정보를 저장한다면 로컬 SQLite에만 두고, 저장 항목은 영상 ID·채널 같은 최소 값으로 한다. 페이지 제목 전체와 URL 전체는 저장하지 않는다. 사용자가 항목별로 보고 지울 수 있어야 한다 (현재는 미구현, Phase 4에서 함께 만든다).
- **확장 권한 최소화** (D를 택할 경우): 호스트 권한을 YouTube 주소로 제한하고, 모든 사이트의 탭 정보를 요청하지 않는다. 호스트 매니페스트의 `allowed_origins`에는 우리 확장 ID 하나만 넣는다.
- **라이선스**: B에 필요한 WinRT 바인딩 패키지와 D의 확장 배포 조건은 **[미확인]**이며, 도입을 결정할 때 확인한다.

## 6. 권고안과 단계

1. **지금**: 변경 없음. 브라우저는 `app:<exe>` 단위를 유지한다.
2. **Phase 4 실험에서 기억 단위를 먼저 정한다** (§7). 프로그램 단위 기억으로도 번역 품질이 충분하면 영상 식별은 필요 없다.
3. 세밀한 단위가 필요하다고 나오면 **B(SMTC)를 먼저** 시도한다. 도입 전에 의존성 승인을 받는다. 식별 결과는 `ContentIdentity`에 `IdentificationMethod.MEDIA_SESSION` 같은 근거로 담고, 박스용 `content_id`는 바꾸지 않는다 (기억용 키를 따로 둔다).
4. B로 부족한 경우(영상 ID가 꼭 필요하거나 탭 오판이 문제인 경우)에만 **D(확장)** 를 설계한다.

3-1에서 만든 `ContentDetector` 인터페이스와 `IdentificationMethod`는 B·D를 더하기에 충분하다. 인터페이스를 바꾸지 않고 어댑터를 추가하면 된다.
