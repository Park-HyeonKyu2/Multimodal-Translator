# Phase 2 감지 설계: OCR 텍스트 기반 감지와 타자 효과 안정화

작성일: 2026-10-10 · 상태: **대부분 구현됨 (2026-10-11), 실제 OCR 연결 전 Mock 기준 검증**

> 같은 날 다중 박스·원문 위치 기준 표시 작업으로 일부가 구현되었습니다.
> - OCR 조각의 위치(`TextSegment`)와 대사 단위 묶기(`application/text_grouping.py`)
> - 텍스트별 ID 추적과 깜빡임 방지 유예(`application/text_display.py`)
> - 여러 원문 일괄 번역(`Translator.translate_batch`)
>
> 아래 "남는 결합" 중 1번(OCR 두 번 실행)과 2번(GPU 경합)은 아직 그대로입니다.
>
> 2026-10-11 처리 파이프라인 안정화 작업으로 다음이 구현되었습니다. 현재 동작은
> [provisional-decisions.md](provisional-decisions.md)의 "자동 감지", "처리 파이프라인"을 기준으로 봅니다.
> - 1번: 자동 감지가 찍은 캡처를 `Frame`으로 OCR까지 넘기고, 같은 캡처 내용의 OCR은 `OcrService`가 재사용합니다.
> - 2번: OCR·번역이 공용 추론 큐(`InferenceScheduler`)에서 동시 실행 수 제한과 우선순위(번역 우선)로 실행됩니다.
> - 타자 효과 안정화: `TextStabilizer`(안정 판단)와 `TextDisplayModel`(중복 번역 판단)으로 나눠 구현했습니다.
> - 감지 정책: 화면이 멈추기를 기다리는 `ChangeTracker` 대신, 바뀌면 간격을 두고 OCR을 요청하는 `ChangeTriggerPolicy`가 기본입니다.
> - 아래 1~2절의 흐름도와 분석은 작성 당시(변경 전) 구조를 설명합니다.

이 문서는 두 가지를 다룹니다.

1. 현재 화면 픽셀 기반 자동 감지의 분석과, OCR 텍스트 기반 감지로 바꾸기 위한 모듈 의존성 점검
2. 타자 효과(글자가 하나씩 나타나는 대사)를 처리하는 텍스트 안정화 알고리즘의 설계, 구현 가능성, 예상 문제

작성 당시에는 Qwen과 PaddleOCR를 연결하지 않았습니다. 아래 내용은 Mock OCR과 가짜 캡처로 검증할 수 있는 범위를 기준으로 합니다.
(2026-10-12 PaddleOCR 연결. 실제 OCR로 안정화 기준을 조정하는 일은 실제 화면 테스트·성능 평가 단계에서 합니다.)

## 1. 현재 픽셀 기반 감지 분석

### 동작 흐름

```
QTimer(0.5초) ─▶ region_provider() ─▶ [워커] capture_region → observer(이미지)
                                                      │
                     ┌────────────────────────────────┘ 관찰값(밝기 지문)
                     ▼
            [UI 스레드] ChangePolicy.observe() ─ True ─▶ translation_needed(영역)
                                                                │
                              coordinator ─▶ controller.request_region(영역)
                                                                │
                              [번역 워커] 다시 캡처 → OCR → 번역 → 결과 창
```

- 관찰값은 박스 안을 96 × 32 격자로 표본 추출한 밝기 지문입니다 (`change_detection.compute_fingerprint`).
- 판단 정책 `ChangeTracker`의 규칙은 "직전과 평균 밝기 차이가 6.0보다 크면 바뀌는 중, 한 번 더 같으면 멈춤, 멈춘 화면이 마지막 번역 화면과 다르면 번역"입니다.

### 강점

- OCR 없이 판단하므로 매우 가볍습니다. 표본 계산은 순수 파이썬이며, 박스 크기와 관계없이 최대 3072개 표본만 봅니다.
- 같은 화면은 다시 번역하지 않습니다. 수동 번역한 화면도 이번 작업부터 기록합니다.
- 캡처 이미지는 지문을 만든 직후 버립니다.

### 한계 (Phase 2에서 OCR 텍스트 기반으로 보완할 부분)

| 상황 | 현재 동작 | 원인 |
| --- | --- | --- |
| 타자 효과 | 대사가 다 나오기 전에 **부분 번역이 여러 번** 일어날 수 있음 | 0.5초 사이 몇 글자만 늘면 바뀐 표본이 적어 평균 차이가 기준(6.0) 아래로 나옴 → "멈춤"으로 오판. 이후 누적 차이가 기준을 넘으면 다시 "바뀜" → 또 번역 |
| 배경이 움직이는 영상 자막 | 번역이 **안 될 수 있음** | 배경 때문에 차이가 계속 기준을 넘어 "멈춤"에 도달하지 못함 |
| 깜빡이는 진행 표시(▼), 커서 | 표시가 클 경우 불필요한 재번역 가능 | 글자와 무관한 픽셀 변화도 변화로 셈 |
| 글자 색 페이드 인/아웃 | 페이드 도중 번역될 수 있음 | 밝기 변화가 점진적이라 단계마다 기준 아래 |
| 같은 문장이 다른 장면에서 다시 나옴 | 직전 번역과 같은 화면이면 건너뜀 | 화면 기준 비교라 문맥 차이를 모름 (AGENTS.md 7장과 관련) |

타자 효과 예시를 계산하면 다음과 같습니다. 400 × 80 박스에서 0.5초에 3글자가 늘면, 바뀐 표본은 전체의 1~3% 정도입니다. 한 표본의 변화량을 200으로 잡으면 평균 차이는 약 2~6이 되어 기준 6.0 이하로 "멈춤" 판정이 나기 쉽습니다. 실제 게임으로 확인한 값이 아니라 계산으로 어림한 값입니다.

## 2. 모듈 의존성 점검

### 이번 작업에서 정리한 것

| 항목 | 변경 전 | 변경 후 |
| --- | --- | --- |
| 관찰 방식 | `_SampleTask`가 `compute_fingerprint`를 직접 호출 | `AutoDetector(observer=...)`로 주입 |
| 판단 정책 | `ChangeTracker` 구체 클래스에 의존 | `ChangePolicy` 프로토콜(observe, mark_translated, restart, reset)에 의존 |
| 오류 메시지 상수 | `auto_detector`가 `controller` 모듈을 import | `core/errors.py`로 옮겨 application 모듈 사이의 의존 제거 |
| 수동 번역 기록 | 없음 (중복 번역 버그) | `AutoDetector.mark_translated(region)` → `ChangePolicy.mark_translated` |

이 변경으로 관찰 방식과 판단 정책만 바꿔 끼우면 감지 방식을 바꿀 수 있습니다. UI, coordinator, 자동 감지 루프는 고치지 않아도 됩니다. `tests/test_auto_detector.py::test_observer_and_policy_can_be_replaced`가 가짜 "텍스트 정책"으로 이를 확인합니다.

현재 계층 의존 방향은 다음과 같고, 위반은 없습니다.

```
ui ─▶ application ─▶ core ◀─ adapters
       (Qt 스레드/시그널)  (모델, 인터페이스)   (MSS, Mock OCR/번역)
```

- core와 adapters는 application이나 ui를 import하지 않습니다.
- application은 ui나 QtGui를 import하지 않습니다.

### OCR 텍스트 기반으로 바꿀 때 남는 결합 (아직 해결하지 않음)

1. **OCR을 두 번 실행**
   - 문제: 감지기가 OCR로 텍스트를 얻어도 `translation_needed`는 영역만 전달합니다. 그래서 번역 파이프라인이 다시 캡처하고 OCR합니다.
   - 제안: `translation_needed(region, observation)`처럼 관찰값을 함께 보내고, `TranslationPipeline`에 이미 인식한 텍스트를 번역하는 진입점(예: `translate_text`)을 추가합니다.
2. **GPU 경합**
   - 문제: 감지기 스레드 풀(1개)과 번역 스레드 풀(1개)이 따로 있습니다. 감지에 OCR을 쓰면 GPU 작업 두 개가 동시에 실행될 수 있습니다.
   - 제안: Notion 02 문서의 "번역 작업 우선, 장면 분석은 저우선" 원칙에 맞춰, application 계층에 우선순위가 있는 공용 추론 큐를 둡니다.
3. **관찰 중 취소 불가**
   - 문제: `Observer` 함수 형태가 `(image) -> 관찰값`이라 취소 토큰을 받지 않습니다. 수백 ms 걸리는 OCR은 stop이나 reset 중에도 끝까지 실행됩니다. 결과는 버려지지만 GPU 시간은 이미 쓴 뒤입니다.
   - 제안: `(image, cancellation)` 형태로 넓힙니다.
4. **수동 번역 기록 비용**
   - 문제: 지금은 별도 표본을 한 번 더 캡처해 기록합니다. OCR 기반에서는 OCR이 한 번 더 듭니다.
   - 제안: 텍스트 정책은 수동 번역 결과의 `source_text`(이미 OCR한 텍스트)를 기록에 그대로 씁니다.
5. **고정 확인 간격**
   - 문제: 간격이 `QTimer` 하나로 고정되어 있습니다. 텍스트 안정화는 상황에 따라 다른 간격이 필요할 수 있습니다(타이핑 중에는 짧게, 대기 중에는 길게).
   - 제안: 정책이 다음 간격을 제안할 수 있게 확장합니다. 필요해지면 그때 추가합니다.
6. **비용 절감용 2단 구성**
   - 문제: OCR을 매 표본마다 돌리면 비쌉니다.
   - 제안: 픽셀 지문을 1차 관문으로 남겨, 화면이 변했을 때만 OCR을 실행합니다. observer가 `(지문, 텍스트 또는 None)`을 반환하는 복합 관찰값으로 구현할 수 있습니다.

## 3. 타자 효과 텍스트 안정화 알고리즘 설계

### 목표

- 글자가 하나씩 나타나는 동안에는 번역하지 않고, **대사가 완성되어 멈추면 한 번** 번역합니다.
- 다음 대사로 바뀌면 다시 기다립니다.
- OCR 인식 결과가 조금씩 흔들려도 같은 대사로 봅니다.

### 입력과 정규화

입력은 표본마다의 OCR 텍스트 `text_t`와 시각 `t`입니다. 비교하기 전에 다음과 같이 정규화합니다.

- 유니코드 NFKC 정규화, 공백과 줄바꿈을 공백 하나로 줄임
- 끝에 붙는 진행 표시와 커서 문자 제거 (예: `▼ ▶ ■ _ |`). 목록은 조정값으로 관리
- 비교용 문자열에서는 대소문자와 문장부호 일부를 무시할지 실험으로 정함

### 상태와 전이

| 상태 | 의미 | 다음 상태 |
| --- | --- | --- |
| `IDLE` | 텍스트 없음 (대사창 닫힘) | 텍스트가 보이면 `GROWING` |
| `GROWING` | 글자가 늘어나는 중 | 같은 텍스트가 연속 k번(또는 T ms) 보이면 `SETTLED` |
| `SETTLED` | 대사가 멈춤 | 커밋 조건을 만족하면 번역 요청 후 `COMMITTED` |
| `COMMITTED` | 번역함 | 다른 대사로 바뀌면 `GROWING`, 텍스트가 사라지면 `IDLE` |

`SETTLED`에서 커밋 조건을 만족하지 못하면(이미 번역한 대사) 번역 없이 `COMMITTED`로 갑니다. `GROWING` 상태가 최대 대기 시간 Tmax를 넘기면 현재 텍스트로 커밋합니다(아래 4번 규칙).

새 텍스트 `n`과 직전 텍스트 `p`의 관계는 세 가지로 판정합니다.

- **같음**: 유사도(정규화 편집 거리 기반) ≥ τ
- **확장**: `p`가 `n`의 앞부분과 거의 같음(OCR 오차 비율 ≤ ε)이고 `n`이 더 김 → 타이핑 중
- **교체**: 같음도 확장도 아님 → 새 대사

### 커밋 규칙

1. `SETTLED`가 되면 커밋 후보입니다.
2. 후보가 마지막 커밋과 **같거나**, 마지막 커밋의 **앞부분**이면(대사 일부가 다시 표시된 경우) 번역하지 않습니다.
3. **교체**가 감지되었는데 직전 `GROWING` 텍스트가 충분히 길고 아직 커밋하지 않았다면, 그 텍스트를 먼저 커밋합니다. 안정 판정 전에 다음 대사로 넘어가는 빠른 진행에서 번역이 빠지지 않게 하기 위함입니다.
4. `GROWING`이 최대 대기 시간 Tmax를 넘기면 현재 텍스트로 커밋합니다(아주 긴 스크롤 텍스트). 이후 확장되면 **전체를 다시 번역해 결과를 교체**합니다.
5. `IDLE`을 거친 뒤(대사창이 닫혔다 열림)나 일정 시간이 지난 뒤에는, 같은 문장도 **새 사건으로 취급**해 기록합니다. 같은 문장이라도 다른 문맥이면 구분해 보존하라는 AGENTS.md 규칙 때문입니다.

### 의사 코드

```python
class TextStabilizer:  # ChangePolicy[str] 구현 예정
    def observe(self, text):
        text = normalize(text)
        if not text:
            self.state = IDLE
            return False
        relation = compare(self.current, text)
        if relation == SAME:
            self.stable_count += 1
        else:
            if relation == REPLACED and self.should_flush(self.current):
                self.pending_flush = self.current        # 규칙 3
            self.current, self.stable_count = text, 0
            self.growing_since = self.growing_since if relation == EXTENDED else now()
        if self.pending_flush:
            return self.commit(self.pending_flush)
        if self.stable_count >= SETTLE_SAMPLES or now() - self.growing_since > MAX_WAIT:
            return self.commit_if_new(self.current)      # 규칙 1, 2, 4
        return False
```

실제 구현은 번역할 텍스트를 반환값에 담아야 합니다. 그래야 위 2절의 "OCR 두 번 실행" 문제를 해결할 수 있습니다.

### 구현할 때 tuning.py에 추가할 조정값 (예상)

| 이름 (안) | 의미 | 출발값 (임시) |
| --- | --- | --- |
| `TEXT_SETTLE_SAMPLES` | 같은 텍스트가 연속으로 보여야 하는 횟수 | 2 |
| `TEXT_SIMILARITY_THRESHOLD` (τ) | 같은 대사로 볼 유사도 | 0.9 |
| `TEXT_PREFIX_ERROR_RATIO` (ε) | 확장 판정에서 허용할 OCR 오차 비율 | 0.15 |
| `TEXT_MAX_GROWING_MS` (Tmax) | 타이핑 중 최대 대기 시간 | 6000 |
| `TEXT_TRAILING_MARKERS` | 제거할 끝 표시 문자 | `▼▶■_|` |
| `TEXT_TYPING_INTERVAL_MS` | 타이핑 중 표본 간격 | 250 |

모두 실험 전 임시값입니다. 구현할 때 `docs/provisional-decisions.md`에도 기록합니다.

### 구현 가능성

- **알고리즘**: 높음
  - 순수 파이썬 상태 기계라 Qt나 모델 없이 단위 테스트할 수 있습니다.
  - "가→가나→가나다→가나다(멈춤)" 같은 OCR 텍스트 시퀀스를 스크립트로 주고 커밋 시점을 검증하면 됩니다.
- **연결**: 높음
  - 이번 작업으로 `ChangePolicy`와 `observer`를 주입할 수 있게 되었습니다.
  - `TextStabilizer`와 OCR observer를 만들어 `AutoDetector`에 넣으면 됩니다.
  - 남은 결합(2절의 1~4번)은 그 전에 정리하는 것이 좋습니다.
- **정확도**: 불확실
  - 실제 OCR 품질, 게임별 글꼴과 효과에 크게 좌우됩니다.
  - PaddleOCR 연결 뒤 실제 화면 녹화로 측정해야 합니다. 녹화본은 저작권 문제가 없는 자료로 한정합니다.
- **비용**: 주의 필요
  - 타이핑 중에는 0.25~0.5초마다 OCR을 돌리게 됩니다.
  - 픽셀 관문(2절의 6번)과 OCR 진행 중 표본 건너뛰기(현재 구조)로 줄여야 합니다.

### 예상 문제와 대응

### 권장 진행 순서

1. 2절의 결합 1~4번을 정리합니다: 관찰값을 함께 전달, 텍스트 번역 진입점, 관찰 중 취소, 결과 텍스트로 기록.
2. `TextStabilizer`를 순수 파이썬으로 구현하고, 스크립트 시퀀스로 단위 테스트합니다 (Mock OCR 단계에서 가능).
3. PaddleOCR 연결 뒤 실제 녹화 화면으로 τ, ε, Tmax를 조정합니다.
4. 픽셀 관문과 OCR 2단 구성으로 비용을 측정하고 조정합니다.
